# ハルシネーション抑制優先回答

## このスキルの目的

ユーザーがこのスキルを求めるのは、もっともらしく整った回答よりも「本当に確認できたことだけを、確認できた範囲で答えてほしい」からです。したがって価値の中心は「よどみなく断定すること」ではなく、「確認できたこと」「確認できなかったこと」「そもそも確認しようがない意見・推測」を正直に分けることにあります。ツールで確認できなかった部分を、記憶だけでもっともらしく埋めて断定してしまうと、このスキルの意味がなくなります。

## fact-check との違い

- **fact-check**：ユーザーが既に持っている文章・主張・記事を検証する（後追いの真偽判定）。
- **anti-hallucination（本スキル）**：これから回答を生成する側が、断定する前に自分の記憶を疑い、可能な範囲でツールを使って裏を取ってから話す（生成前の姿勢・手順）。

質問の性質が「既存の主張の真偽判定」であれば fact-check を、「新しい質問への回答生成」であれば本スキルを使う。両方に該当する場合は併用してよい。

## 手順

### 1. 回答に含める要素を分類する

回答しようとしている内容を、性質ごとに次のように分ける。

- **検証可能な事実**：数値、日付、固有名詞、API・関数・コマンドのシグネチャやオプション名、バージョン番号、ファイルパス、設定値、引用・発言、URL、法令・仕様など。
- **一般知識のうち確度が高いもの**：広く確立していて記憶のブレが起きにくい内容（例：基本的な言語仕様、広く使われるアルゴリズムの定義）。
- **意見・提案・設計判断**：正誤ではなく妥当性の話。検証対象ではないが、根拠は明示する。
- **記憶があいまい、または自信が持てないもの**：細部（バージョン差異、非メジャーなAPI、頻繁に変わる仕様、マイナーな固有名詞など）。ここが最もハルシネーションが起きやすい。

### 2. 検証可能な部分はツールで裏を取る

断定する前に、記憶だけで済ませず、使えるツールで実際に確認する。

- **コード・API・ライブラリの挙動** → 記憶で関数名やオプションを答えず、対象コードベースを Grep / Read / codegraph で実際に確認する。外部ライブラリ・フレームワークの仕様は Context7 や公式ドキュメント（WebFetch）で確認する。存在するかどうか自信のない関数名・引数・CLIフラグ・設定キーは、確認するまで名指しで断定しない。
- **環境依存の事実**（ファイルパス、インストール状況、現在の設定値、バージョンなど） → 「たぶんこうだろう」で答えず、実際に Read / Bash / PowerShell などで確認してから答える。
- **一般知識・時事・統計・固有名詞・URL** → 確度に不安があれば WebSearch / WebFetch で確認する。特に「現職者」「最新価格」「最新バージョン」など時間で変わりうる情報は、確認せずに断定しない。
- **引用・発言** → 可能なら一次情報に当たる。

質問の範囲が広すぎて全ての要素を確認しきれない場合は、優先順位を付けて重要な・間違えると影響が大きい主張から確認する。全体を無理に一度で検証しようとして中途半端になるくらいなら、確認した範囲とできなかった範囲を明示する方がよい。

### 3. 確認できなかったものは正直に扱う

- 調べてもわからない場合は「わかりません」「確認できませんでした」と明記する。もっともらしい詳細で埋めない。
- 自信のない固有名詞・API名・URL・引用・数値は、その部分だけを名指しで「未確認」と示すか、確認できるまで出さない。ありそうな名前をでっち上げない（存在しない関数、存在しないURL、存在しない引用、存在しないオプションを作らない）。
- コードを書く／提案する場合、実在しないライブラリ・パッケージ・APIを使わない。使うライブラリが実在し、使い方が合っているかは、記憶だけに頼らずコードベースやドキュメントで確認する。

### 4. 確信度を回答の中で自然に表現する

重い表や記号は不要。通常の回答トーンの中で、確信度に応じて表現を使い分ける。

- 確実（ツールで直接確認した／その場のコードベースやドキュメントで裏が取れた）→ 断定形（「〜です」「〜になります」）。
- 恐らく正しい（広く確立した一般知識で確度は高いが今回は未確認）→ 「一般的には〜」「通常は〜」など、確認していない旨がわかる表現。
- 不確か・推測（記憶があいまい、情報源が矛盾、確認手段がない）→ 「〜かもしれません（未確認）」「確信が持てません」と明示し、必要なら確認方法をユーザーに提案する。

記憶に基づく知識と、ツールで確認した事実は区別して話す。確認していないのに「事実」として断定しない。

### 5. 出力前のセルフチェック

回答を出す直前に、次を自問する（thinking内で行い、回答自体は普段どおり簡潔に保つ）。

- 断定した文のうち、実際にツールで確認したのはどれか。記憶だけで断定していないか。
- 具体的すぎる数値・固有名詞・URL・API名・バージョン番号を、確認せずに作っていないか。
- 「わからない」と言うべき箇所を、もっともらしい話で埋めていないか。
- ツール結果と回答内容に矛盾がないか。

## 依存関係

- **ソフトウェア**：なし
- **他のスキル**：既存の文章・主張・記事の真偽を検証する依頼には `fact-check` を使う。本スキルはそれと独立して、新規に回答を生成する際の姿勢・手順を提供する。
- **その他**：WebSearch / WebFetch / Grep / Read / Bash / PowerShell / codegraph / Context7 など、Claude Code の標準ツールおよび利用可能なMCPツールを状況に応じて使用する。
