# 共有フォルダ ポータル生成

## このスキルが解決する問題

共有フォルダにファイルやプロジェクトが増えると、目的のファイルにたどり着くまでフォルダを何階層も掘る必要が出てくる。フォルダのルートに、カテゴリ別・検索可能な自己完結HTMLポータルページを1枚生成し、そこから各ファイル・フォルダへワンクリックでアクセスできるようにする。

**重要な制約:** ファイル数が多い共有フォルダでは、画像(.png/.jpg等)、Office文書(.xlsx/.pptx/.docx等)、PDF、Jupyter Notebook(.ipynb)、モデル重み(.pth/.ckpt等)、`__pycache__`、ログ、巨大CSV等の中身を一切Readしない。トークンを浪費するだけでなく、多くの場合バイナリで読めない。構造把握は`find`/`ls`（メタデータのみ）、説明文の材料集めは`README.md`等の軽量テキストファイルの先頭数行のみに限定する。

## 手順

### 1. 対象フォルダを特定する

パスが指定されていなければ、現在の作業ディレクトリを対象にする。`ls`/`find -maxdepth 1` でトップレベル構成を確認し、`.git`、`__pycache__`、`node_modules`、`desktop.ini`、隠しファイル・隠しフォルダは調査対象から除外する。

### 2. 構造を軽量に調査する（ファイル内容は読まない）

- `find <対象> -maxdepth 2〜4 -not -path '*/.*'` 等で階層構造を把握する。深いプロジェクトツリー（機械学習の実験フォルダ等）は depth を浅めに留め、末端まで律儀に列挙しない。
- `find <対象> -type f | wc -l` で規模感を把握し、数千件規模なら「個別ファイルを全部カード化」ではなく「意味のある単位（プロジェクトフォルダ／カテゴリフォルダ単位）でカード化」する方針に切り替える。
- 各サブフォルダに `README.md` があるかを機械的にチェックし（`for d in */; do [ -f "$d/README.md" ] && echo "$d"; done` 等）、あれば**Readツールで先頭5〜15行程度だけ**読んでタイトル・概要をつかむ。README がない場合は、`find -maxdepth 1 -type f` で見えるファイル名（例: `particleFilter.py`, `NMF_mnist.py`）から内容を妥当に推測して一文で説明する。無理に断定できない場合はファイル名をそのまま使う。

### 3. カテゴリ分けする

トップレベルのフォルダ（部署、案件、プロジェクト種別など）ごとにセクションを作る。サブプロジェクトが多いフォルダ（例: 個人の実験コード置き場）は、その内側でさらにカードを並べる1段のグリッドにする。ファイル数が少ないフォルダ（数個程度）は個別ファイルをそのままカード化してよい。

**業務効率化ツールは1カテゴリに集約する。** 社内で共有されている業務効率化ツール（ローカルアプリ〈.exe/.msi等〉、Webアプリ、Power Platformツール〈Power Apps/Power Automate/Power BI等〉、Claude Skillsなどのスキル集、マクロ・アドイン、社内向けCLI/スクリプト集など）は、フォルダ構造上どこに散らばっていても（部署別・案件別フォルダの奥に個別に置かれていても）、元の場所ごとにセクションを分けず、ポータル上では「業務効率化ツール」のような1つの共通カテゴリセクションにまとめてカード化する。トップレベルのフォルダ構成をそのまま機械的にセクション化するのではなく、種別（ツール類かどうか）を優先してグルーピングする。

### 4. ポータルHTMLを生成する

- **Artifactツールは使わない。** Artifact は外部ホスティングされ CSP でローカルファイルへのリンクが機能しないため、このスキルの目的（ローカル共有フォルダ内のファイルへ実際に飛べること）を満たせない。**Writeツールで対象フォルダのルート直下に直接HTMLファイルを作成する**（ファイル名例: `ポータル.html`）。
- 自己完結の単一HTML（インラインCSS/JS）。ライト/ダークモード両対応（`prefers-color-scheme`）。
- 上部に検索ボックスを置き、各カードの`data-search`属性とカード本文テキストに対して部分一致でフィルタするJSを実装する（該当0件時のメッセージも用意する）。
- カードはfolder用/file用でアイコンを分け、タイトル・簡潔な説明・（あれば）補足メタ情報を表示する。
- リンクは**相対パス**にする（`file://`を決め打ちしない。ポータルHTML自体が対象フォルダ内にあるため相対参照で足りる）。
  - フォルダへのリンクは末尾に`/`を付ける。ブラウザは`file://`のディレクトリに対してネイティブの「〜のインデックス」一覧表示を出せるため、深い階層まで手作業で列挙する必要はない。各セクション見出しにも「フォルダを開く」リンクを添える。
  - パスに半角スペース・日本語・記号が含まれる場合はURLエンコードする（スペース→`%20`、日本語→`%E3...`等）。手で書く場合はブラウザの開発者ツールや`encodeURIComponent`相当の変換結果を使い、生成後に一つはクリックして実際に開けるか確認する。
- **フォルダ表示はページ遷移させず、ポータル内に常駐する埋め込みパネル（`<iframe>`）で開く。** 素朴に `<a href="folder/">` をそのまま辿らせると、ブラウザのネイティブ「〜のインデックス」ページに完全に遷移してしまい、ポータルへ戻る手段がブラウザの戻るボタン頼みになる。そこで固定表示のパネル（トップに「← ポータルに戻る」ボタンと現在パスの表示、任意で「新しいタブで開く」リンクを持つツールバー＋`<iframe>`）を1つ用意し、フォルダ系のリンク（カードの`href`、「フォルダを開く」リンク）はクリック時に`preventDefault()`して`iframe.src`を差し替え、パネルを表示する形にする。「戻る」ボタンでパネルを閉じてカード一覧に戻す。
  - **ファイルカードは既定で `target="_blank" rel="noopener"` を付けて直接リンクする（デフォルト方針）。** これによりExcel/PowerPoint/PDF等のバイナリはブラウザの標準挙動としてダウンロードされる（ブラウザの仕様であり、この方法では回避不可）が、ポータル自身のタブは開いたままなので「戻る」はタブ切り替えで済む。**「ファイルカードのクリック先を親フォルダにして埋め込みパネルで表示する」という迂回策は採用しない** — 一見ダウンロードを避けられそうに見えるが、結局そのパネル内でファイルをクリックした瞬間に同じダウンロードが発生するだけで実質的な解決にならないことを実装・検証済み。ダウンロードされずに**既定のデスクトップアプリで直接開く**ようにするには、`HKCU\Software\Classes\<独自スキーム>` にカスタムURLプロトコルを登録し、`Start-Process`で開く小さなスクリプトを紐づける以外の方法がない（ブラウザの仕様上の制約）。これはレジストリへの変更を伴うため、**ユーザーが明示的に希望した場合のみ**、変更内容（キーのパス、スクリプトの場所、削除すれば元に戻せること）を具体的に説明した上で確認を取ってから実施する。ユーザーがレジストリ変更を望まない場合は、素直に「新しいタブで開く（ダウンロードされる場合がある）」という直接リンクに留める。
- フッターに生成日時と、更新方法（ファイルが増えたらこのスキルを再実行するか、該当セクションにカードを手動追加する旨）を一言添える。

### 5. 確認と報告

作成したファイルパスを報告する。可能なら `start` (Windows) やBashの `start ""` でデフォルトブラウザに開いて見た目を確認する。ユーザーには「重いファイルは開いていない」ことを一言添えると安心材料になる（本スキル自体が前提としている制約だが、確認を求められることがあるため）。

## 注意点

- 既にポータルHTMLが存在する場合は、全面作り直しではなく差分更新（新しいフォルダ/ファイルのカード追加、変わったものの説明更新）を優先する。
- パスワードや秘密鍵、認証情報らしきファイル名（`.env`, `credentials`, `secret`等）を見つけた場合は、ポータルに掲載する前にユーザーに確認する。
- 対象がgitリポジトリの場合、`.git`配下やビルド成果物・依存関係ディレクトリ（`node_modules`, `venv`, `__pycache__`等）はポータルに載せない。

## 依存関係

依存関係なし。`find`/`ls`等のシェルコマンドとRead/Writeツールのみで完結し、追加のソフトウェア・ライブラリ・他スキルは不要。
