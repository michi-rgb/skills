# arXiv ディープリサーチ

arXiv **だけ** を情報源に、あるテーマの先行研究を系統的に集めて整理し、
日本語の Markdown レポートを作る。出典は arxiv.org（および alphaXiv 経由で
取得した arXiv 論文）に限定する。

## 大原則（必ず守る）

1. **arxiv 限定**。arxiv.org 以外を出典にしない。Google Scholar・
   Semantic Scholar・出版社サイト・ブログ等は引用しない。arXiv に載っていない
   事項は「arXiv の範囲では確認できない」と明記し、外部知識で埋めない。
   alphaXiv 系のツール（`get_paper_content` `answer_pdf_queries`）は
   Semantic Scholar の URL も受け付けてしまうことがあるが、渡す URL は必ず
   arxiv.org / alphaxiv.org のものに限定し、それ以外には使わない。
2. **捏造ゼロ**。引用してよいのは API が実際に返した論文だけ。記憶を頼りに
   arXiv ID・タイトル・著者・年・要旨をでっち上げない。ID は必ず取得結果から
   コピーする。少しでも不確かなら、その論文には触れない。
3. **事実・推論・私見を区別**。各記述を「論文がそう述べている事実」「複数論文
   からの合理的な推論」「あなた（生成AI）の推測・解釈」に分けて示す。
4. **不確実性を明示**。検索の網羅性・分野の偏り・件数などに自信が持てない箇所は
   断定しない。数値・日付・固有名詞は取得データに基づき、曖昧なら曖昧と書く。
5. **arXiv の性質を踏まえる**。多くはプレプリント（査読前のことがある）。
   API は被引用数を返さない。分野により収録の濃淡が大きい（cs・物理・数学・
   stat・eess 等が厚く、医学・人文社会等は薄い）。英語論文に偏る。これらの
   限界をレポート末尾に必ず書く。

## アクセス手段

### 優先: alphaXiv コネクタ（MCP）

alphaXiv の論文取得ツール（`discover_papers` `get_paper_content`
`answer_pdf_queries`。任意で `read_files_from_github_repository`）が使える
環境では、これを**第一の手段**として使う。arxiv.org ドメインかどうかを
毎回フィルタする必要がなく、要旨・著者・日付が構造化データとして直接返る
ため、`web_search` + `web_fetch` の組み合わせより手数が少なく、値の転記
ミスも起きにくい。

1. **検索（discover_papers）**: `keywords`（3〜4語の完全一致向けキーワード）
   と `question`（テーマの詳細な意味的説明）を渡す。`difficulty`
   （1〜10）は調査の広さ・深さに応じて上げる（広く俯瞰したいテーマや
   マイナーな分野ほど高めにし、複数ラウンドの探索を促す）。
   1回の呼び出しに頼らず、言い換え・上位/下位概念・別表記（略語と
   正式名称の両方）で複数回呼んで候補プールを広げる方針は従来と同じ。
2. **候補の確定**: 返ってきた論文の arXiv ID・タイトル・著者・要旨は、
   **返却結果からのみ転記**する（記憶で補完しない）。arXiv 以外の論文が
   紛れていないかは念のため確認する。
3. **内容確認（get_paper_content）**: 個々の論文の URL（abs / pdf /
   alphaxiv.org のいずれか）を渡し、構造化サマリまたは全文（`fullText: true`）
   を取得する。要旨レベルの確認はここで足りることが多い。
4. **精読・裏取り（answer_pdf_queries）**: より踏み込んだ確認（手法の詳細、
   数値、実験設定など）が要る論文には使う。**同一論文への質問はまとめて
   1回の呼び出しに全部詰める**（ツール側の説明でも「ほぼ無料」とされている
   ため、論文ごとに何度も呼び直すのは非効率）。返ってくるページ引用を
   そのままレポートの根拠にできる。
5. **重複排除**: arXiv ID で重複を除く。

### フォールバック: arxiv.py（alphaXiv コネクタが使えない環境用）

alphaXiv の MCP ツールが使えない場合、`web_search`/`web_fetch` の代わりに、
本スキル同梱の `scripts/arxiv_fallback.py`（[lukasschwab/arxiv.py](https://github.com/lukasschwab/arxiv.py)
のラッパー）で arXiv API に直接アクセスする。これは alphaXiv と同じく
構造化データ（ID・タイトル・著者・要旨・日付・カテゴリ）を返すため、
`web_search` + `web_fetch` より手数が少なく転記ミスも起きにくい。

事前確認: `python -c "import arxiv"` がエラーなく通ればそのまま使える
（未インストールならユーザーに確認のうえ `pip install arxiv requests pypdf`）。

1. **検索（search）**: キーワード・カテゴリ・日付範囲・IDリストを指定して
   JSON配列を標準出力に得る（進捗・件数は標準エラー出力）。

   ```powershell
   python <このスキルのパス>/scripts/arxiv_fallback.py search "diffusion model" `
       --max-results 30 --category cs.LG --category cs.CV `
       --sort-by submittedDate --date-from 2024-01-01
   ```

   - `query` は省略可（その場合 `--id-list` が必須）。スペースを含む場合は
     フレーズ検索（`all:"..."`）になる。
   - `--category` は複数指定でOR結合（例 `cs.LG` と `cs.CV` の両方）。
   - `--date-from`/`--date-to`（`YYYY-MM-DD`）は `submittedDate` の範囲指定。
   - `--sort-by`（`relevance`/`lastUpdatedDate`/`submittedDate`）・
     `--sort-order`（`descending`/`ascending`）。
   - 言い換え・上位/下位概念・別表記ごとに複数回呼んで候補プールを広げる方針は
     alphaXiv 使用時と同じ。
   - `--delay`（既定3.0秒）は arXiv API 利用規約により3秒未満にしない。
2. **候補の確定・重複排除**: 出力JSONの `arxiv_id`（バージョン付き）または
   `arxiv_id_base`（バージョンなし）で重複を除く。ID・タイトル・著者・要旨は
   **この出力からのみ転記**する（記憶で補完しない）。
3. **ID指定での再取得**: 候補が固まったら `--id-list 2005.14165,1706.03762`
   （カンマ区切り、`query` 省略可）で該当論文だけを再取得できる。
4. **精読（必要な論文のみ）**: 要旨で足りない場合、PDFを取得して本文テキストを
   確認する。

   ```powershell
   python <このスキルのパス>/scripts/arxiv_fallback.py text 2005.14165 --outdir <一時フォルダ> --first 1 --last 5
   ```

   機械的なテキスト抽出のため、レイアウト崩れ・数式や表の抜けが起こり得る
   （読んだ範囲を明示し、抽出テキストを鵜呑みにしない。疑わしい箇所は
   `--outdir` に保存された元PDFを直接確認する）。PDFだけ保存したい場合は
   `pdf` サブコマンドを使う。
5. いずれの経路でも arXiv 以外のドメインは候補プールに含めない
   （このスクリプトは arxiv.org のAPI/PDFのみを叩く）。

**HTTP 429/503（レート制限）が出た場合**: arxiv.py 側で自動リトライ後もエラーなら
スクリプトが日本語メッセージで打ち切る（スタックトレースは出さない）。実行環境の
IPが混雑していると数分単位で解消しないこともある。数十秒〜数分待って1クエリだけ
再実行し、直っていれば `--max-results` を抑えめにしたまま残りのクエリへ進む。
連続でクエリを打つときも `--delay` を下げない（既定3秒未満は不可）。

## ワークフロー

### 1. スコープ確定
テーマ・期間・対象カテゴリ・粒度（広く俯瞰か、特定手法を深くか）を把握する。
依頼が曖昧なら前提を勝手に置かず、必要に応じて一度だけ簡潔に確認する。

### 2. クエリ設計（1本でなく複数）
言い換え・上位/下位概念・別表記（略語と正式名称の両方）でクエリを分散させる。
alphaXiv コネクタが使える場合は `discover_papers` の `keywords`/`question` を
複数パターン用意する（例：「拡散モデル」なら `diffusion model` /
`score-based` / `denoising` をそれぞれ別の呼び出しにする）。フォールバック時は
同じ考え方で `arxiv_fallback.py search` の `query`/`--category` を
言い換え・別表記ごとに複数回呼び分ける。

### 3. 取得
alphaXiv コネクタが使える場合は各クエリを `discover_papers` で実行し、
返ってきた論文を候補プールに集める（新しさを見たいときは `question` に
年（例 `2025`/`2026`）を含める）。使えない場合は `arxiv_fallback.py search`
を各クエリで実行し、返ってきたJSONを候補プールに集める（新しさを見たい
ときは `--sort-by submittedDate` や `--date-from` を使う）。いずれの経路でも
arXiv ID で重複排除する。
arxiv 以外のドメイン・出典は候補プールに含めない。

### 4. スクリーニング（選別）
要旨を読み、テーマ適合・新規性・代表性で重要論文を絞る。被引用数は arXiv からは
得られないので代用しない（古典的・基盤的かどうかは要旨やジャーナル参照から慎重に
推測し、推測である旨を残す）。何件ヒットし何件採用したかを記録する。

### 5. 精読（必要に応じて）
特に重要な論文は要旨だけでなく本文まで確認してよい（これは arxiv 内のため
原則に反しない）。alphaXiv コネクタが使える場合は `get_paper_content` で
構造化サマリ・全文を取得し、さらに踏み込んだ確認が要る論文は
`answer_pdf_queries` にその論文への質問をまとめて1回で投げる。フォールバック時は
abs ページや PDF を arxiv.org から `web_fetch` する。読んだ範囲を明示し、
読めていない部分を断定しない。

### 6. 実装コードの確認（任意）
手法の再現性やアルゴリズムの詳細を裏取りしたい場合、論文が GitHub リポジトリを
公開していれば `read_files_from_github_repository` で該当箇所を確認できる。
必須の手順ではないので、必要と判断したときだけ行う。使った場合はレポート中で
「実装コードを確認: [リポジトリ URL]」のように出典を明示する。

### 7. 統合
テーマ別・手法別・時系列などで整理し、合意点・対立点・トレンド・空白
（未解決問題）を抽出する。各主張に必ず根拠論文の arXiv ID を紐づける。

### 8. レポート作成
下記テンプレートで Markdown ファイルを作り、`/mnt/user-data/outputs/` に保存して
`present_files` で提示する。

## レポート構成（この雛形に従う）

```markdown
# [テーマ] — arXiv ディープリサーチ

> 情報源: arXiv API のみ / 作成日: [YYYY-MM-DD] / 言語: 日本語
> 検索対象カテゴリ: [...] / 検索期間: [...]

## 要約
（3〜6文。何が分かったか。確度の高い結論と、まだ不確かな点を分けて。）

## 調査方法
- 使ったクエリ（実際の search_query を列挙）
- 並び順・取得件数・採用件数
- スクリーニング基準

## 主要な発見
（テーマ別の小見出し。各記述に [arXiv:ID] を付す。
 「論文の主張」と「複数論文からの推論」「私見」を文中で区別する。）

## 主要論文一覧
| arXiv ID | タイトル | 著者(筆頭ほか) | 投稿/更新 | 主カテゴリ | 一言メモ |
|---|---|---|---|---|---|
| 2005.14165 | ... | Brown ほか | 2020-05 | cs.CL | ... |
（ID・タイトル・著者・日付は取得結果からのみ転記。リンクは abs_url を使う。）

## トレンドと未解決の論点
（時系列の流れ、対立する立場、まだ埋まっていない空白。推論には根拠 ID を。）

## 限界と注意（必須）
- arXiv のみ・プレプリント中心（査読前を含む）・被引用数なし
- 分野/言語の収録偏り・検索網羅性の限界（取りこぼしの可能性）
- 確証が弱い箇所の列挙
- 最新性・所属・採否など時間で変わる情報は別途の確認を推奨

## 参考文献（arXiv）
[arXiv:ID] 著者. タイトル. 主カテゴリ. abs_url
（API が返した論文のみ。1件ずつ ID と URL を対応させる。）
```

## よくある失敗（避ける）
- 記憶からそれらしい ID・年・著者を補完する → 厳禁。取得結果のみ。
- 1クエリだけで「網羅した」と書く → 複数クエリ＋限界明記。
- 被引用数や「最も影響力のある」を断定 → arXiv からは得られない。推測なら推測と書く。
- arxiv 外の知識を混ぜる → 原則違反。混ぜるなら「arXiv 外」と明示し出典を切る。
- 略語をそのまま使う → 初出で正式名称（必要なら和訳）を併記する。
- alphaXiv コネクタが使えるのに気づかず `web_search`/`web_fetch` だけで進める
  → 手数が増えて非効率。まず `discover_papers` 等が使えるか確認する。
- `answer_pdf_queries`・`get_paper_content` に arxiv.org / alphaxiv.org 以外の
  URL（Semantic Scholar の abs ページ等）を渡す → 「arxiv 限定」原則に反する。
- 同じ論文に `answer_pdf_queries` を質問ごとに何度も呼び直す → 質問はまとめて
  1回に詰める（複数質問はほぼ追加コストがかからないとツール側で説明されている）。
