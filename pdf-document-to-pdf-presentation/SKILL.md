# PDF文書 → PDFプレゼン変換

段落主体のPDF文書を、**要点に絞った日本語のスライド（PDF）**に変換する。
ゴールは「元文書を読んでいない聴衆が、スライドをめくるだけで話の流れと結論を
つかめる」状態。文章は主要な論点に圧縮し、**元PDFの図はすべて使い**、視覚的な
分かりやすさと発表としての流れを最優先する。

この変換は要約ではなく**再構成**である。原文の段落をそのまま写すのではなく、
「この文書は結局何を主張しているか」を掴んだ上で、聴衆に見せる順序と粒度に
組み替える。細かい数式の導出・脚注・参考文献・冗長な前置きは大胆に落とし、
主張・理由・図・結論を残す。

## 出力とテーマ

- 出力: `<出力先>/<PDF名>.pdf`（スライド、16:9）。指定がなければ元PDFと同じ場所に作る。
- テーマ: クリーン学術系（白基調・ネイビーのアクセント・セリフ無しの明快な見出し）。
- 言語: **常に日本語**。原文が日本語以外なら翻訳する。固有名詞・記号・式は原綴りを保つ。

## 生成の仕組み（役割分担）

スライドの体裁（配色・レイアウト・図の内接配置・通し番号）は付属スクリプトが
担う。**あなたの仕事は「中身の設計」＝スライドプラン(JSON)を書くこと**に集中する。
これにより毎回の見た目が安定し、あなたは内容の圧縮と流れの構成に集中できる。

- `scripts/extract.py` … 元PDFからページ画像・テキスト層・図候補を切り出す
- `scripts/build_deck.js` … プランJSON → `.pptx`（クリーン学術系テーマ）
- `scripts/make_pdf.py` … プランJSON → `.pptx` → `.pdf`、さらにQA用サムネイル

依存はサンドボックスに用意済み（`node`+`pptxgenjs`、LibreOffice、poppler、Pillow、
Noto Sans CJK JP フォント）。`pip install`/`npm install` は不要。スクリプトは
グローバルnpmのパスを自前で解決する。

## 手順

### 1. 全体把握（構成・言語・図の所在をつかむ）

まずページ画像とテキスト層を出し、**Readツールで元PDFを20ページずつ通読**して
文書の骨格を掴む。ここを飛ばすと圧縮も流れの設計もできない。

```bash
PDF=/path/to/input.pdf
DIR=/path/to/work            # 中間生成物の作業フォルダ
python3 <skill>/scripts/extract.py pages "$PDF" "$DIR" --dpi 150
```

読みながらメモする:

- 文書のタイプ・主題・想定読者、そして**一言でいう主張**
- 章・節の見出し階層（プレゼンの「節（section）」の候補になる）
- 図表番号の体系（Figure 3 / 図3 / Table 1）と**どのページにどの図があるか**
- 文書全体の言語（日本語以外なら翻訳方針を決める）
- 落としてよい部分（細かい導出・脚注・謝辞・参考文献・重複説明）

長い文書（数十ページ以上）でも、スライドは文書全体を等倍でなぞらない。
**重要な節を選び、そこに図とともに焦点を当てる。** 何を入れ何を落とすかの
取捨選択こそがこのスキルの核心。

### 2. 図の抽出と検品（図は全部使う）

```bash
python3 <skill>/scripts/extract.py figures "$PDF" "$DIR"
```

`images/fig_pNNN_M.png` が出る。これは**機械的な候補**なので、**必ずReadで
複数枚まとめて開いて検品**する（1枚ずつ往復すると遅い）:

- 本物の図・グラフ・回路図・模式図・写真 → **採用（原則すべて）**。
- 表 → 画像は消し、スライド上でテキスト/簡易表として作り直す（複雑すぎる場合のみ画像採用）。
- ロゴ・罫線・飾り・数式の一部などのゴミ → 削除。
- 欠け・隣接要素の混入・粗すぎ → `crop` で切り直す。ページ画像(150dpi)の
  ピクセル座標で指定し、結果をReadで確認して座標を詰める:

```bash
python3 <skill>/scripts/extract.py crop "$PDF" "$DIR" --page 42 --box 100,350,980,900 --suffix m1
```

検出一覧にない図（薄い写真・スキャン図版）に気づいたら同じ方法で足す。
**「図は全て使う」が原則**なので、自動検出の取りこぼしは検品で拾う。ただし
装飾ロゴやページ全体のスキャン画像など「図として意味を持たないもの」は除く。

図は最終的にプランJSONから**プラン基準の相対パス**で参照するので、採用した図は
出力PDFの隣に置く `images/` にまとめておくと取り回しやすい。

### 3. スライドの流れを設計する（プレゼンの背骨）

聴衆が迷わない順序を先に決める。標準の骨格:

1. **タイトル**（`title`）… 文書タイトルの日本語訳＋一言サブタイトル＋出典
2. **目次**（`agenda`）… これから話す3〜6個の柱
3. 柱ごとに **節扉**（`section`）→ **内容スライド**（`content`）数枚
4. **まとめ**（`summary`）… 主張・結論・含意を3〜5点

流れの設計で意識すること:

- **1スライド＝1メッセージ。** タイトル（見出し）はその1枚で言いたいことを
  体言止めや短い主張文で言い切る（「〜の3つの要因」「Xは〜で決まる」）。聴衆は
  見出しだけ追っても筋が通るようにする。
- **節は3〜6個**に収める。多すぎる章立てはプレゼンの流れを崩す。近い節は束ねる。
- 図は**それを説明する本文の近く**に置く。図が主役の節では図中心のスライドにする。
- 論理の接続（だから/しかし/一方で）を見出しや箇条書きの並びで感じさせる。

### 4. 文章の圧縮（中くらいの粒度）

主要な論点は残しつつ、細かい数式・脚注・実装詳細は省く。目安:

- **1スライドの箇条書きは3〜5個**、各項は原則1行（長くて2行）。
- 完全な文よりも**要点の言い切り**。助詞や修飾を削っても意味が通るなら削る。
- 数式は「何を意味するか」を1行の日本語にする。式そのものを見せるのは、それが
  その節の主役のときだけ。
- 図から読み取れること（グラフの傾向など）は本文で繰り返さない。図に語らせる。
- 元が英語等なら**自然な日本語**に翻訳する。直訳調にしない。専門用語は定訳＋
  必要なら原語を括弧書き。図の中の文字は原則そのまま（描き直さない）。

### 5. プランJSONを書く

`build_deck.js` が読むプランを書く。型と最小例だけ以下に示す。**全フィールドと
レイアウト自動判定の詳細は `references/plan_schema.md` を読むこと。**

```json
{
  "theme": "academic",
  "footer": "文書タイトル（短縮可）",
  "slides": [
    {"type":"title","title":"…","subtitle":"…","meta":"出典: input.pdf ・ 2026"},
    {"type":"agenda","items":["背景","理論","結果","含意"]},
    {"type":"section","number":1,"title":"背景"},
    {"type":"content","kicker":"背景","title":"1枚で言い切る見出し",
      "bullets":[{"text":"要点1"},{"text":"補足","level":1},{"text":"要点2"}],
      "figure":{"path":"images/fig_p003_1.png","caption":"図1: 内容の日本語補足"}},
    {"type":"summary","title":"まとめ","bullets":["結論1","結論2","含意"]}
  ]
}
```

- 図は `figure`（1枚）か `figures`（複数）で参照。**採用した図は必ずどこかの
  スライドに載せる**（図は全部使う原則）。図には内容を1行で述べる日本語 `caption`
  を付ける（原図＋日本語補足キャプション）。
- `layout` は省略で自動判定（図とテキストの有無で最適配置を選ぶ）。意図がある
  ときだけ `text` / `text-figure` / `figure` / `figures` / `two-col` を明示。
- はみ出しを避けるため、1スライドに詰め込みすぎない。情報が多い節は**スライドを
  分ける**。

### 6. 生成する

```bash
python3 <skill>/scripts/make_pdf.py plan.json /path/out.pdf --thumbs
```

`out.pdf`（スライド）と `out_thumbs.png`（全ページのサムネイル格子）ができる。

### 7. QA（必ず目視する）

**`out_thumbs.png` をReadで開いて全ページを点検する。** 見るべき点:

- 文字が枠からはみ出していないか、図とテキストが重なっていないか
- 図が歪んで/切れていないか、意図した図が載っているか（抜けが無いか）
- 見出しだけ追って話の流れが通るか、日本語が自然か、誤変換・文字化けが無いか

問題があればプランJSONを直して再生成する（詰め込みすぎのスライドは分割、粗い
図は `crop` で取り直し）。**崩れが無くなるまで直す。** 目視を省略しない——
機械配置は多くを吸収するが、詰め込みすぎと図の取り違えだけは人が見ないと気付けない。

### 8. 納品

完成PDFを成果物フォルダに置き、`present_files` でユーザーに渡す。作業用の
`pages/`・中間pptx・サムネイルは中間生成物なので納品物には含めない（消してよい）。

## フォント指定

既定は `Noto Sans CJK JP`。プランの `font`（と任意で `fontHead`）で変更できる。ただし
**PDFはサンドボックス上の LibreOffice で描画される**ため、指定フォントがそこに無ければ
自動代替され、指定どおりにならない。游ゴシック・ヒラギノ等の商用/OS付属フォントは通常
この環境に無い。ユーザーが特定フォントを希望したら、`fc-list :lang=ja` で実在を確認し、
無ければ正直に伝えて選択肢を示す（近い無償フォントで代替する／編集可能な pptx も渡して
手元PCで書き出してもらう）。詳細は `references/plan_schema.md`。

## 図が乏しい文書・リスト主体の文書

対象が論文・マニュアルではなく、目次・プログラム・名簿・カタログのような**羅列主体で
本物の図がほとんど無い文書**のこともある。その場合は全ページを等倍でなぞらず、
**概要・ハイライトの集約版**を作る（大会の会期・会場・セッション構成・代表項目・統計など、
聴衆が全体像をつかめる形）。無理に図を捏造しない。どの範囲・粒度にするか判断に迷うときは
ユーザーに方針を確認する（要約の対象は変わりやすいので勝手に前提を置かない）。

## つまずきポイント

- **テキスト層は当てにしすぎない。** 2段組の順序崩れ・合字・ハイフネーションで
  壊れることがある。**ページの見た目（Readで開いた元PDF）を正とし**、抽出テキストは
  固有名詞・数値・綴りの確認に使う。`extract.py pages` が「破損」と警告したら
  テキスト層は捨て、視覚読みだけで書く。
- **スキャンPDF**（全ページが1枚画像）では `figures` は候補を出せない。手順2の
  自動検出に固執せず、`crop` で必要な図版を手で切り出す。本文はページ画像の
  視覚読みで書く。
- **図の取り違え防止。** どのスライドにどの `fig_*` を載せたか、検品時に対応を
  メモしておく。QAでサムネイルと照合する。
- **色は6桁HEX・`#`なし**（スクリプト側の制約）。プランで色は指定しない。
- 生成が失敗したら `make_pdf.py` の代わりに `build_deck.js` を単体実行すると
  エラー箇所（どのスライドか）が出る。
