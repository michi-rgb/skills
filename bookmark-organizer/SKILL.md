# ブックマーク整理

## このスキルが解決する問題

NETSCAPE-Bookmark-file-1形式のエクスポートファイルは、各項目に `ICON="data:image/png;base64,...."` という長大なbase64データが埋め込まれており、ファイルサイズの大半（数十〜100万トークン級）を占める。素朴に対象ファイルを丸ごとReadしたり、リネーム後の内容を丸ごとWriteし直したりすると、コンテキストとトークンを浪費する。本スキルは、**アイコンデータを一度もモデルの出力に通さずに**タイトル変更とフォルダ再構成を行う手順を提供する。

また、ユーザーは「ネットワーク通信量を抑えて」と明示していなくても、各リンク先に逐一WebFetchしてタイトルを確認するのは過剰である。URLのドメインと既存のタイトル文字列から内容を推測してリネームすれば十分であり、これがデフォルトの動き方。ユーザーが「実際のページを見て正確なタイトルにして」等、明示的に要求した場合のみWebFetchで確認する。

## 手順

### 1. 対象ファイルを特定する

パスが指定されていなければ、作業ディレクトリや会話で言及されたファイルをGlobで探す（`*.html` 等）。ファイル冒頭（先頭数行のみRead、または `<!DOCTYPE NETSCAPE-Bookmark-file-1>` をGrep）でNetscape形式であることを確認する。

### 2. 構造をトークン効率よく抽出する（絶対にファイル全体をReadしない）

3系統のGrepを別々にかける。**URLとタイトルを1つの正規表現で同時に取ろうとしないこと** — `HREF="..."[^>]*>` のように書くと `[^>]*` がICON属性のbase64全体を貪欲にマッチしてしまい、マッチ自体が巨大になって出力が省略されたり大量のトークンを消費したりする。必ず分離する。

- フォルダ見出しと階層: `<DT><H3` および `</DL>` を `output_mode: content, -n: true` でGrep。インデント幅（先頭スペース数）から親子関係を読み取る。
- URL一覧: パターン `HREF="([^"]+)"` を `-o: true` で抽出（1行1URL、ICON部分に触れないので軽量）。
- タイトル一覧: パターン `>([^<]{1,300})</A>` を `-o: true` で抽出。上限文字数はタイトルが長い項目（論文タイトルなど）を取りこぼさないよう十分大きく取る（120程度だと長いタイトルが数件マッチせず抜け落ちることがある）。

行番号（`-n`）を揃えておくと、URL/タイトル/フォルダの対応づけが機械的にできる。

### 3. リネーム案とフォルダ構成案を作る

抽出したURL・現在のタイトル・フォルダ名から、各項目にとって「一目で内容が分かる」簡潔な日本語（または元の言語に合わせた）タイトルを考える。判断基準:

- サイト名 + 内容の要点（例:「New chat」→「ChatGPT」、長い論文タイトル→「論文: 〇〇」）
- URLのクエリパラメータやセッションID、`?utm_...` 等のマーケティングパラメータはタイトルに含めない
- 既存フォルダ構成に妥当性があるなら極力維持し、無秩序に増えた「フォルダに属さない項目」だけを新設フォルダにまとめるなど、変更を必要最小限にする（ユーザーの元の分類意図を尊重する）
- 内容が推測できない項目は無理に断定せず、判明している範囲の名前を維持する
- **並び順（フォルダ・項目とも）**: 元ファイルの出現順をそのまま踏襲せず、テーマ・用途が近いフォルダ同士／項目同士が隣り合うように並べ替える。例えば「開発ツール」フォルダと「ドキュメント・API仕様」フォルダは離さず隣接させる、同一サービス（例: GitHub関連の複数リンク）は連続させる、といった形で、後から見て関連物をまとめて見渡せる順序を設計する。フォルダ内の子フォルダ・アイテムが混在する場合も同様に、関連する子フォルダとアイテムが近くに来るよう配置する。

大きめのブックマーク集合（数十件以上）では、この設計作業を Task/Agent (fork) に任せてもよいが、最終的なリネーム表とフォルダツリーはこのスキルを実行しているエージェント自身が把握しておく（次のステップで plan.json に落とし込むため）。

### 4. plan.json を作成する

`scripts/rebuild.py` が読む形式で、次の内容を書き出す（Writeツールでスクラッチパッドに保存）:

```json
{
  "renames": { "https://example.com/": "新しいタイトル" },
  "folders": [
    {
      "name": "フォルダ名",
      "add_date": "1234567890",
      "last_modified": "0",
      "attrs": "",
      "items": ["https://a/", "https://b/"],
      "children": [ { "name": "サブフォルダ", "items": ["https://c/"] } ]
    }
  ]
}
```

- `add_date` / `last_modified` / `attrs` は省略可（省略時は `"0"`）。既存フォルダを維持する場合は、Grepで取得したそのフォルダの元の `ADD_DATE`/`LAST_MODIFIED` をそのまま使うと日時情報が保たれる。
- `folders` 配列・`children` 配列・`items` 配列はいずれも**そのまま出力順になる**。手順3で設計した並び順（関連性の高いフォルダ・項目が隣り合う順序）をここでそのまま反映すること。元ファイルでの出現順に引きずられて機械的に並べない。
- お気に入りバー（ツールバー）フォルダを維持する場合は `"attrs": " PERSONAL_TOOLBAR_FOLDER=\"true\""` を指定する。
- **ファイル内に存在する全てのhrefを、plan.json中のどこかに過不足なく1回ずつ登場させること。** 抜け漏れがあると `rebuild.py` が実行を拒否する（安全装置）。

### 5. rebuild.py で安全に書き換える

```powershell
python "<このスキルのパス>\scripts\rebuild.py" --src "<対象HTMLファイル>" --plan "<plan.json>"
```

このスクリプトは:
- 元ファイルからhref単位で `ADD_DATE` / `ICON` 等の属性とタグ全体を抽出し、タイトルだけを差し替える（アイコンデータをモデルが再生成する必要が一切ない）
- 書き換え後のhref集合が元ファイルと完全一致するか（欠落・重複がないか）を検証し、不一致なら書き込みを拒否する
- `--dst` を省略した場合、上書き前に `<元ファイル名>.backup-YYYYMMDD-HHMMSS.html` として自動バックアップを作成する

### 6. 結果を軽量に確認する

丸ごとReadせず、Grepで抜き打ち確認する:
- `<DT><H3` をGrepしてフォルダ一覧を確認
- `HREF="[^"]*"[^>]*>[^<]*</A>` を `sed 's/ICON="[^"]*"//'` 等でICON部分を除去しつつ数十行プレビュー
- 件数チェック: `grep -c '<DT><A HREF=' 元ファイル` と新ファイルを比較し、一致することを確認

### 7. ユーザーに報告する

変更点の要約（リネーム方針、新設・統合したフォルダ）と、バックアップファイルのパスを伝える。バックアップは自動削除せず、ユーザーの判断に委ねる。

## 注意点

- このファイルは `<!-- DO NOT EDIT! -->` という注釈が入っているが、これはブラウザが「自動生成ファイルなので手で編集するとブラウザに上書きされる」ことを警告しているだけで、エクスポートされた静的ファイルを整理する分には問題ない。ただし、ブラウザに再インポートする運用であることが前提なので、変更後にどう反映するか（再インポートが必要か）はユーザーの環境依存であり、必要なら確認する。
- HTML特殊文字（`&`, `<`, `>`）を含む新しいタイトルを付けるときは `&amp;` 等に適切にエスケープする。
